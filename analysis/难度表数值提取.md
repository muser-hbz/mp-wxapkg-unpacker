## 一、核心 DDA 表（动态难度调整）

### 1.1 LevelCond —— 挑战次数条件表（7 条）

由 `DynamicLevel_Utils.getLevelCondCfg(ratio, challengeCounts)` 匹配。`cond1`=难度比(广告/挑战)区间，`cond2`=挑战次数区间，`base×ratio` 计入策略分。

| id | cond1 (ratio) | cond2 (challengeCounts) | base | ratio | itemCounts | resurrection | popCounts |
|----|---------------|--------------------------|------|-------|------------|--------------|-----------|
| 1 | [0,99999] | (10,99999] | 100 | 6 | 3 | 1 | 2 |
| 2 | [0,99999] | (9,10] | 100 | 5 | 3 | 1 | 2 |
| 3 | [0,99999] | (7,9] | 100 | 4 | 3 | 1 | 2 |
| 4 | [0,99999] | (5,7] | 100 | 3 | 3 | 1 | 2 |
| 5 | [0,99999] | (3,5] | 100 | 2 | 3 | 1 | 2 |
| 6 | [0,99999] | (1,3] | 100 | 1 | 3 | 1 | 2 |
| 7 | [0,99999] | [0,1] | 100 | 0 | 3 | 1 | 2 |

**解读**：`cond1` 全为 `[0,99999]`，即难度比不做过滤，**仅由挑战次数 `challengeCounts` 决定**。挑战次数越多（玩家越卡）→ ratio 越大 → 计入分越高。挑战 >10 次得 600 分，≤1 次得 0 分。

### 1.2 StayDay —— 留存天数条件表（4 条）

由 `getStayDayCfg(stayDays)` 匹配，`cond3`=玩家停留天数区间。

| id | cond3 (stayDays) | base | ratio |
|----|-------------------|------|-------|
| 1 | [3,99999) | 100 | 6 |
| 2 | [2,3) | 100 | 4 |
| 3 | [1,2) | 100 | 2 |
| 4 | [0,1) | 100 | 0 |

**解读**：停留 ≥3 天得 600 分，<1 天得 0 分。老玩家/留存越久，计入分越高。

### 1.3 Strategy —— 策略输出表（7 条）

由 `getStrategyCfg(score)` 匹配，`cond1`=策略分区间，输出对棋盘元素的**叠加调节量**。

| id | cond1 (score) | fruitTypeCount | quistFlowerCount | holeCount | holeFruit | iceCount | iceLog | blockCount | ropeCount | fireCount |
|----|---------------|----------------|------------------|-----------|-----------|----------|--------|------------|-----------|-----------|
| 1 | [0,100) | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 |
| 2 | [100,200) | -1 | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 |
| 4 | [200,300) | -2 | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 |
| 6 | [300,400) | -3 | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 |
| 7 | [400,500) | -4 | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 |
| 9 | [500,600) | -5 | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 |
| 10 | [600,99999] | -6 | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 |

**解读**：本表中**只有 `fruitTypeCount` 被调节**（其余元素全为 0）。策略分越高 → 水果种类减少越多（最多 -6 种）。

### 1.4 DDA 评分公式与实例

```
score = LevelCond.base × LevelCond.ratio  +  StayDay.base × StayDay.ratio
最终 fruitTypeCount = 基础关 fruitTypeCount + Strategy.fruitTypeCount   (封顶 MaxFruitTypeCount=36)
```

`LevelCond.ratio` 范围 0~6（贡献 0~600），`StayDay.ratio` 范围 0~6（贡献 0~600），总分 0~1200，但 Strategy 最高桶为 `[600,99999]`，故 **score ≥ 600 即触顶 -6 种水果**。

| 玩家画像 | challengeCounts | stayDays | score | 水果种类调节 |
|----------|------------------|----------|-------|--------------|
| 新手首通 | 1 | 0 | 0+0=0 | 0（不变） |
| 轻微卡关 | 4 | 1 | 200+200=400 | -4 |
| 严重卡关+老玩家 | 12 | 3 | 600+600=1200 | -6（触顶） |
| 严重卡关+新玩家 | 12 | 0 | 600+0=600 | -6（触顶） |

**核心设计结论**：DDA **只降不升**——玩家越卡关、留存越久，水果种类越少，关卡越简单。即"动态帮弱"，避免玩家流失。其它机制元素（洞/冰/障碍/绳/火/问号花）在当前配置中不参与 DDA 调节。

## 二、模式内难度曲线表（随分数动态加速）

### 2.1 ClassicDifficulty —— 经典/传统模式（34 条）

按当前分 `point` 匹配，控制下落间隔 `time`(ms) 与速度 `speed`，`group`=可用方块组（始终 1-10）。

| point | time(ms) | speed | point | time(ms) | speed |
|-------|----------|-------|-------|----------|-------|
| 0 | 350 | 1000 | 10000 | 100 | 400 |
| 500 | 350 | 900 | 15000 | 100 | 300 |
| 1000 | 350 | 800 | 20000 | 100 | 200 |
| 2500 | 350 | 650 | 25000 | 100 | 100 |
| 5000 | 300 | 500 | | | |

**规律**：分数越高 → `time` 从 350ms 降到 100ms（下落更频繁），`speed` 从 1000 降到 100（数值越小下落越快）。分数 25000+ 时达到极限难度。

### 2.2 DropDifficulty —— Drop 掉落模式（33 条）

按 `point` 匹配，控制速度 `speed` 与可用方块组 `group`，含教学引导 `guide`/`img`。

| point | speed | group | 阶段说明 |
|-------|-------|-------|----------|
| 0 | 3 | 3 5 9 12（4种） | 教学：向下划动落下方块 |
| 10 | 3 | 3 5 9 12 | 教学：左右划动移动方块 |
| 120 | 4 | 1 2 3 4 5 6（6种） | 教学：单击屏幕方块变形 |
| 360 | 6 | 1-8（8种） | |
| 600 | 7 | 1-11（11种） | |
| 840 | 8 | 1-14（14种，满） | |
| 2000 | 10 | 1-14 | |
| 10000 | 26 | 1-14 | |
| 30000 | 46 | 1-14 | |
| 60000 | 52 | 1-14 | 极限（img=Txt_011） |

**规律**：`speed` 从 3 单调增至 52；`group` 从 4 种逐步解锁到 14 种满集。分数 840+ 后种类不再增加，仅提速。引导文案证实 Drop 模式为**滑动操控的 1010! 式方块放置**（放满一行或一列消除）。

### 2.3 TetrisCountRate —— 方块计数权重表（26 条）

`getRandomCfgByWeight` 用，`count`=当前该类方块已生成数，`rate`=下次生成权重。

| count | rate | count | rate | count | rate |
|-------|------|-------|------|-------|------|
| 0-3 | 1 | 12-17 | 20 | 22-23 | 60 |
| 4-8 | 5 | 18-20 | 30 | 24 | 1 |
| 9-11 | 10 | 21-23 | 60 | 25 | 0 |

**规律**：已生成越多 → 权重越高（鼓励同类聚集，便于成行消除），到 count 21-23 达峰值 60；count 24 骤降到 1，25 降为 0（硬上限，禁止再生成）。

## 六、难度设计总结

1. **三层 DDA（仅 Normal 主模式，AB-B 组生效）**：
   - 第1层 `LevelCond`×`StayDay` → 评分（挑战次数 + 留存天数）
   - 第2层 `Strategy` → 输出 `fruitTypeCount` 调节（-6~0，只降不升）
   - 第3层 `FlowStrategy` + `GameSpread` → 分布策略（简单/正常/困难）+ 种类百分比微调
   - 封顶 `MaxFruitTypeCount=36`

2. **模式内曲线**：Classic/Drop 模式按实时分数动态提速 + 解锁方块种类（`ClassicDifficulty`/`DropDifficulty`/`PointArea`），`TetrisCountRate` 控制同类聚集权重。

3. **棋子布局**：`FruitData` 定义 381 种火锅食材（radius≈40），`FallItemMgr` 用 Poisson-disk 采样（radius=81）生成不重叠位置，`GameSpread_Utils` 按 DDA 选 6 种分布策略分配水果 ID。

4. **关卡总量**：`LevelData` 320 关，基础 fruitTypeCount 3~36，DDA 最多再减 6。
