## 一、整体架构定位

`__APP__/game.js`（2.28MB）经核对**仅为 Cocos Creator 引擎 + 启动引导代码**，真正的玩法逻辑全部在子包 `_subpackages_main_/subpackages/main/game.js`（1MB，274 个脚本类，已被压缩混淆为 4 行）。

从 `app-config.json` 与场景路径 `db://assets/tetris/ui/fruit/GameScene.fire`、以及 `GameConst.js` 可知：这是一款 **水果主题的多模式消除游戏**，包含 5 种游戏模式：

| GameType | 值 | 皮肤 | 玩法 |
|---|---|---|---|
| Puzzle 拼图 | 101 | puzzle | 1010!式方块放置（用 `cubeData` 17 种形状 + 整行整列消除） |
| Adventurous 冒险 | 102 | puzzle | 同上 |
| **Drop 掉落** | 103 | drop | **物理掉落 + 点两个相同水果消除（主玩法，FallItemMgr）** |
| Day 每日 | 104 | puzzle | 拼图 |
| Tradition 经典 | 105 | classic | 传统俄罗斯方块式 |

棋子类型（prefab config）：`BlockItem`/`FallItem`/`HoleItem`/`StumpItem`/`RopeItem`，加上 `FK_BombItem`（炸弹）、问号花、冰块等机制元素。

## 二、棋子动态布局算法（核心：Drop 模式）

布局由 `FallItemMgr.js` 统一管理，分**位置生成**与**种类分配**两步。

### 2.1 位置生成 —— Poisson-Disk 泊松盘采样

核心方法是 `generatePoints(width, height, radius, k)`：

```js
generatePoints(e,t,i,o){
  var n=i/Math.sqrt(2), s=Math.ceil(e/n), r=Math.ceil(t/n),  // 网格尺寸 = radius/√2
      a=new Array(s*r).fill(-1), l=[], c=[],
      u=new cc.Vec2(Math.random()*e, Math.random()*t);       // 初始随机点
  for(this.addPoint(u,a,l,c,n,s); c.length>0;){
    var _u=Math.floor(Math.random()*c.length), _d5=c[_u];
    var _h2=!1;
    for(var _f2=0; _f2<o; _f2++){                              // 每点尝试 k 次
      var _o44=Math.random()*Math.PI*2, _u2=Math.random()*i+i, // 环带 [r, 2r]
          _f3=new cc.Vec2(_d5.x+Math.cos(_o44)*_u2, _d5.y+Math.sin(_o44)*_u2);
      if(...&&this.isPointValid(_f3,a,l,n,s,r,i)){ this.addPoint(_f3,a,l,c,n,s); _h2=!0; break; }
    }
    _h2||c.splice(_u,1);                                       // 失败则移出 active 表
  }
  return l;
}
```

这是经典的 **Bridson 泊松盘采样**：用 `radius/√2` 的背景网格加速近邻查询（`isPointValid` 只检查 3×3 相邻格），在 `[radius, 2·radius]` 环带上随机投点，保证任意两水果中心距 ≥ `radius`(=81px)，**生成均匀且不重叠的随机布局**。`itemPool` 不足时还会 `spawnFruitsVertical` 自动补充坐标。

掉落方向 `downType`：0=纵向下落、1=横向右、2=横向左，由关卡配置决定（`getVerticalWidth`）。

### 2.2 特殊关卡固定布局

部分关卡用固定坐标而非采样（`loadLevel`）：
- `level1()`：第 1 关教学固定 12 个位置
- `centerStumpLevel()`：每 10 关的第 2 关且偶数轮，中央树桩布局
- `scatterFruits1~4()`：4 种预设散布形态
- `fruitScliceLevel1()`/`sliceSpreadLevel()`：水果切片模式

### 2.3 水果种类分配 —— GameSpread_Utils（难度核心）

位置定好后，调用 `GameSpread_Utils.getIds(count)` 生成"哪个位置放哪种水果"的 ID 数组。这是**难度算法落地的关键环节**，详见第三节。

### 2.4 机制元素布局

- **洞穴 Hole**：`spawnFruitsVertical` 中绑定洞主水果，`getHoleCountArr` 按基数均分 + 随机余数分配每个洞的水果数
- **冰块 Ice**：`checkIce` 随机选位置，冰块消除对数 = `DynamicLevel_Utils.getIceLog()` 叠加
- **障碍物 Block**：`checkBlock` 在两侧按 500 间距放置
- **树桩 Stump**：`checkStumpItem` 每 10 关第 2 关放置
- **问号花**：`updateFlowerCount` 随机标记

## 三、难度算法 —— 三层动态难度调整 (DDA)

游戏实现了**三套叠加的动态难度系统**，全部由 `FK_ABTestMgr` 的 AB 测试开关控制（仅 B 组生效），并通过 `Level_Utils.js` 汇总后注入布局。

### 第 1 层：DynamicLevel_Utils —— 元素数量调节

`DynamicLevel_Utils.js` 基于玩家行为**增减棋盘元素数量**。

**难度比计算**（`getCountsDiffcultRatio`）：
```js
ratio = advertCounts / challengeCounts   // 看广告次数 / 挑战次数（challengeCounts=0 时为 0）
```

**策略评分**（`getCurStrategyCfg`）：
```
score = LevelCond.base × LevelCond.ratio  +  StayDay.base × StayDay.ratio
```
- `LevelCond` 由 (ratio, challengeCounts) 区间匹配（`isCondRange` 解析 `[a,b)`/`(a,b]` 数学区间）
- `StayDay` 由玩家停留天数匹配

**输出**：由 score 匹配 `Strategy` 配置，返回 9 个调节量：`fruitTypeCount`(水果种类)、`quistFlowerCount`(问号花)、`holeCount`/`holeFruit`(洞穴)、`iceCount`/`iceLog`(冰块)、`blockCount`(障碍)、`ropeCount`(绳子)、`fireCount`(大火)。

**注入**：`Level_Utils.getFruitTypeCount/getHoleData/getIceCount...` 将这些值**叠加到原始关卡数据**上（封顶 `MaxFruitTypeCount`）：
```js
getFruitTypeCount(){
  var e=this.getLevelData().fruitTypeCount;
  if(e>0){ e += DynamicLevel_Utils.getFruitTypeCount();        // 叠加 DDA
           var max = NormalCfg_Utils.getMaxFruitTypeCount();
           e>max && (e=max); }                                  // 封顶
  return e;
}
```
关卡变更时 `setHistoryLevel` 重置计数器。

### 第 2 层：FlowStrategy_Utils —— 用户分群分发

`FlowStrategy_Utils.js` 把玩家分成 8 类，决定**用哪种分布策略**和**水果种类微调百分比**。

**用户类型判定**（`getUserType`，按优先级）：

| 类型 | 判定条件（关键常量） | 处理 |
|---|---|---|
| CrossDayLogin 跨天登录 | 距上次游戏 ≥40 小时 | 简单分布 `getIdsSpreadB`，送 3 次挑战 |
| MultiDayStuck 连续多日未通关 | 连续 5 天每日有效挑战≥3 且未通关 | 简单分布；种类 -10%/-20%（按未通关天数 4/≥5） |
| FirstDaySecondLevel 首日第2关 | 首日+第2关+总挑战>4+未看广告 | 权重随机选简单/正常分布 |
| NotPassLevel 卡关 | 当关挑战≥30 & 有效≥20 & 广告≥15 | 正常分布，种类 **-10%** |
| NoAdWatch 不看广告 | 关卡>10 且当前/上一关均无广告 | 种类 +adjust%；连续≥3 关有概率走**困难分布** |
| LowAdWatch 看广告少 | 关卡>6 & 注册≥1天 & 广告/挑战≤0.15 | 种类 **+8%/+16%** |
| NormalAdWatch 正常看广告 | 近 5 天日均广告 3~20 | 按当日/均值比 ±调节（封顶 ±20%） |
| Default 默认 | 无特殊条件 | 正常分布 |

关键常量（文件末尾）：`NO_AD_TYPE_ADJUST_MAX=0.2`、`DEDUCT_TYPE_COUNT=3`、`DAILY_HISTORY_MAX_DAYS=5`、`MULTI_DAY_STUCK_DAYS=5` 等。看广告/挑战次数通过 `addAdCount`/`addValidChallengeCount`（进度阈值 `CHALLENGE_PROGRESS_THRESHOLD=0.25`）持续累计并写本地存储。

### 第 3 层：GameSpread_Utils —— 实际 ID 序列生成

`GameSpread_Utils.js` 是难度算法的最终落地，包含 **6 种分布策略**：

**① `getFruitTypes(typeCount)`** —— 应用第 2 层的种类调节：
```
NotPassLevel → -10% ; MultiDayStuck → 0/-10%/-20%
LowAdWatch → +8%/+16% ; NoAdWatch → +min(20%, 4%×无广告通关次数)
NormalAdWatch → ±动态%
```
封顶 `MaxFruitTypeCount`，再随机洗牌生成种类 ID 池。

**② `getIds(count)` 路由** 按 AB 开关选子策略：
- `getIdsSpread2_0`（v2.0 正常）：分 0-10%/10-30%/30-50%/50-100% 进度段，**早期用少种类（6 种）、后期逐步引入新种类**，全程保证水果成对（偶数），奇数种类向后段传递配对
- `getIdsSpread3_0`（v3.0 高密度，DensitySpread AB）：更细的 0-10/10-30/30-40/40-65/65-100 段，40-65% 大批量成对投放
- `getIdsSpread4_0`（v4.0 进度，ProgressSpread AB）：0-10/10-20/20-30/30-50/50-100，种类比例 40%→60% 渐进
- `getIdsSpreadB`（**简单分布**，spreadType=Simple）：用加权随机 `getNextFruitId`，权重 `30+10×(半数-序号)` 偏向少数种类，给弱势玩家
- `getIdsSpreadHor1/Hor2`：横向模式专用
- **`getIdsFromDifficulty`（困难分布，spreadType=Difficult）**：当 `downType=0 && count>150 && fruitTypeCount>15` 时，**先扣除 `DEDUCT_TYPE_COUNT=3` 种最难的水果**，用剩余种类生成正常分布，再把这 3 种**插入到序列最末尾（棋盘底部）及倒数 60~80 位置**——使最难匹配的水果堆积在底部，加剧通关难度。

**③ `getFlowStrategyVerticalIds` 总路由**：按第 2 层用户类型选策略——CrossDayLogin/MultiDayStuck→简单；NoAdWatch→按 50:10×连续关数 权重在正常/困难间随机；其余→正常。

### 难度算法整体数据流

```
原始关卡表(FK_Cfg.LevelData)
   │  fruitTypeCount, holeCount, iceCount, blockCount, targetCount, downType...
   ▼
[第1层] DynamicLevel_Utils  ── ratio=广告/挑战, +stayDays ──►  +元素数量
   ▼
[Level_Utils] 叠加+封顶  ──►  最终 fruitTypeCount / hole / ice / block ...
   ▼
[第2层] FlowStrategy_Utils ── 行为分群 ──►  userType + 种类调节%
   ▼
[第3层] GameSpread_Utils.getFruitTypes  ──►  实际种类ID池
        GameSpread_Utils.getIds        ──►  按userType选分布策略 → ID序列(保证成对/渐进)
   ▼
[FallItemMgr] Poisson采样位置 × ID序列 → 实际棋盘  +  holes/ice/blocks/stumps
```

## 四、消除与计分

- **消除规则**：点两个相同水果即消除（match-2），物理引擎 `cc.RigidBody` 驱动下落；`onCheckItemContact` 中 **地板堆积 >10 个即判负**（`Match_Play_Lose`）
- **连胜/连消**：`FK_SeriesRemove.js` 播放 "lianxiao" spine 动画 + 数字
- **计分**：`FK_CubeRemoveScore.js` 区分普通分与奖励分（带 "×" 倍数）；`FK_RewardRemoveScore.js` 显示 "+score"
- **道具**：刷新（`onMatchBoosterRefresh` 按难度分段加权洗牌）、收集、一键收集、复活（`reviveNormal` 用 Poisson 式安全位置重置）
- **拼图模式**：`TetrisUtils.js` 的 `removeMapHV` 实现整行整列消除，`calConnectedCmpInMap` 用 DFS 计算连通块；方块形状定义在 `GameConst.cubeData`（17 种俄罗斯方块矩阵）

## 六、结论

这款游戏的核心技术亮点是**一套精细的三层动态难度系统**：
1. **DynamicLevel_Utils** 用「广告/挑战比 + 留存天数」调节棋盘元素数量；
2. **FlowStrategy_Utils** 把玩家分为 8 类行为画像，决定分布策略与种类微调（弱势玩家降种类、白嫖玩家升种类）；
3. **GameSpread_Utils** 提供 6 种水果分配算法（简单/正常/高密度/进度/困难/横向），通过**进度分段 + 成对保证 + 渐进引入种类**控制单局内难度曲线，困难分布还会把最难水果压到棋盘底部。

布局上用 **Poisson-disk 泊松盘采样**保证水果均匀不重叠，配合物理引擎实现下落消除。
